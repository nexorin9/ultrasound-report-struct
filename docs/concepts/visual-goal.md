# 视觉目标卡 · 超声报告结构化系统

> 本产品是**常驻运行的单一可执行文件**，没有图形界面（无 Web 控制台 / SPA / TUI）。
> 因此「视觉目标」= **终端会话本身**：一个停在小程序的后台进程，处理完一份报告追加一行结构化日志，
> 每隔一轮输出一次心跳计数。本卡是给实现立靶子的对照物，**不是**宣传图。
>
> 本环境不具备图像生成能力，故只提供本结构化卡片；`docs/screenshots/` 里的真实运行截图在收尾阶段采集，
> 两者**不得**互相冒充。

---

## 一、三个状态

### 状态 1 · 起始态（刚启动，目录为空）

画面上有什么：

- 一行启动自检结论，逐条列出检查项与结论：词典文件可读、状态库父目录可写、必需凭据齐备 / 缺哪个变量名。
- 一行心跳，四个计数全为 0：`processed=0 failed=0 awaiting_review=0 pending_writeback=0`。
- 屏幕右侧留白，无滚动、无弹窗、无表格。

```
{"ts":"2026-10-31T09:10:00+08:00","level":"INFO","event":"startup_checks","dictionary":"ok","state_db":"ok","credentials":"ok"}
{"ts":"2026-10-31T09:10:00+08:00","level":"INFO","event":"heartbeat","processed":0,"failed":0,"awaiting_review":0,"pending_writeback":0}
```

### 状态 2 · 首个可用瞬间（一份含「左肾 3.2cm」的报告到达）

画面上有什么（按出现顺序）：

1. **一行接收**：哪个检查号的报告被取出（`report_received`）。
2. **一行解析结果**：抽到几条、失败几条；成功条目带统一值与换算路径，失败条目带原文行列。
3. **一行失败定位**：把没认出来的项指回原文，例如「单位缺失 @ 第 7 行第 12 列」。
4. **一行对拍结果**：该患者同侧部位上次值与差值；没有历史就明写「首次」。
5. 心跳行刷新，计数从 0 变成实际值。

```
{"ts":"2026-10-31T09:12:03+08:00","level":"INFO","event":"report_received","study_no":"<STUDY_NO>"}
{"ts":"2026-10-31T09:12:03+08:00","level":"INFO","event":"report_parsed","study_no":"<STUDY_NO>","items":3,"failed":1}
{"ts":"2026-10-31T09:12:03+08:00","level":"WARN","event":"item_failed","study_no":"<STUDY_NO>","error_code":"UNIT_MISSING","line":7,"column":12,"raw":"左肾积水 3.2"}
{"ts":"2026-10-31T09:12:03+08:00","level":"INFO","event":"compared","study_no":"<STUDY_NO>","item_code":"kidney.hilum_ap","previous_value":28,"delta":4,"direction":"增大"}
{"ts":"2026-10-31T09:12:04+08:00","level":"INFO","event":"heartbeat","processed":1,"failed":1,"awaiting_review":1,"pending_writeback":0}
```

### 状态 3 · 成形态（常驻运行、医师已确认一轮）

画面上有什么：

- 心跳行稳定滚动，四个计数持续变化：`processed` / `failed` / `awaiting_review` / `pending_writeback`。
- 失败条目按**错误码**聚合可查（值班运维回答「昨天有多少报告没解析出来、卡在哪一环」）。
- 医师确认后，多出一条**回写**与一条**推送**记录，状态从「待确认」变为「已回写」。
- 回写失败时，出现告警行与 `pending_writeback` 计数 +1，而不是静默。

```
{"ts":"2026-10-31T09:20:11+08:00","level":"INFO","event":"review_confirmed","study_no":"<STUDY_NO>","reviewer":"超声科医师"}
{"ts":"2026-10-31T09:20:11+08:00","level":"INFO","event":"emr_written","study_no":"<STUDY_NO>","items":3,"status":"written_back"}
{"ts":"2026-10-31T09:20:12+08:00","level":"INFO","event":"wecom_pushed","study_no":"<STUDY_NO>","status":"ok"}
{"ts":"2026-10-31T09:20:13+08:00","level":"INFO","event":"heartbeat","processed":42,"failed":3,"awaiting_review":2,"pending_writeback":0}
```

## 二、视觉语言

| 维度 | 取值 |
|------|------|
| **画面类型** | 终端会话（服务运行日志）——与已锁定的「事件驱动守护」交付形态一致 |
| **配色** | 无自绘配色。沿用终端默认前景色；语义靠**日志级别字段**区分（`INFO` / `WARN` / `ERROR`），不靠颜色块 |
| **字体族** | 终端等宽字体；数值与检查号用等宽对齐，便于纵向扫读 |
| **信息层级** | 一级：心跳计数行（每轮一条，恒定出现在末尾）→ 二级：单份报告的接收 / 解析 / 对拍 / 回写行 → 三级：失败明细行（含错误码与行列号，最长但最需要精确定位） |
| **留白密度** | 每份报告 4–6 行，不加空行分组；心跳行与明细行之间空 1 行即可 |
| **对齐** | 全部为单行 JSON，不做多列对齐表格——**列对齐在等宽终端里不可靠**，字段顺序稳定即可 |

## 三、必须可达的约束（不许画出现有依赖做不出来的效果）

- **只允许出现**终端里的纯文本行：结构化日志行、心跳计数行、`cargo run -- export` 打印的导出路径。
- **禁止**任何图形元素：图表、进度环、仪表盘、三维视图、动画、颜色渐变、表格框线对齐（终端宽度不可控）。
- **禁止**出现不来自真实处理结果的画面元素（例如伪造的曲线图、「示意图」占位）。
- 日志字段集合固定为：时间 / 级别 / 事件码 / 检查号 / 计数 / 错误码 / 行列号 / 原文片段片段——**每一条都必须能从真实产物里取到**。
- 画面里出现的数值（统一值、差值、计数）**必须**与 `docs/screenshots/` 里的实测截图一致；不一致时以实测为准，本卡作废。

## 四、与实测截图的关系

| 侧 | 位置 | 内容 |
|----|------|------|
| **视觉目标** | 本文件 | 目标画面：日志字段、事件顺序、层级与密度 |
| **实测证据** | `docs/screenshots/` | 真实运行截图：实际终端渲染、真实导出内容、真实回写摘要 |

**诚实标注**：目标是「应该长什么样」，实测是「实际长什么样」。本产品以终端日志为主，差距主要出现在**措辞与字段顺序**（实现可能调整事件码命名或字段位置）以及**行数**（真实处理一份报告可能产生多于 6 行的输出）。**不得**声称两者完全一致，也**不得**为抹平差距事后绘制「效果图」充充实测截图。
